# Marketplace Asset Studio

Thunder Visual IDE includes a package authoring workspace for assets that can be distributed independently of the IDE. Open **Marketplace → Asset Studio…** from the main editor.

The first marketplace asset types are:

- View form themes
- HTML snippets for the HTML Component Designer

The studio is intended for free, commercial, private and marketplace packages. It gives each package a stable ID and metadata, validates the source, previews it in a sandbox and exports a self-contained ZIP file.


## Studio workspace controls

The Asset Studio uses three priority columns: the asset library, package editor, and live preview/checks. The package editor intentionally starts narrower so the asset list and preview have more room. Click a column header’s expand button to make that column occupy the workspace and collapse the other two into labelled rails. Click the focused column’s button again to restore the normal three-column layout, or click another rail button to focus that column directly.

Every HTML, CSS, JavaScript, and component-template editor has an **Expand** button. It opens the IDE's full CodeMirror editor above the Asset Studio with the matching language mode, then writes the saved source back into the package and refreshes the preview. Custom package source is editable in both compact and expanded views. Built-in source remains read-only but can be selected and copied for inspection.

## Built-in and custom packages

Bundled assets are loaded from:

```text
form-themes/
html-snippets/
```

These packages are read-only in the Asset Studio. They cannot be edited, replaced, exported from the custom package controls or deleted.

Custom packages are stored under:

```text
storage/marketplace/form-themes/<package-id>/
storage/marketplace/html-snippets/<package-id>/
```

Custom packages can be edited, deleted, imported and exported. A built-in asset can be used as a starting point with **Create Custom Copy**, which creates a new ID and never modifies the original files.

Built-in definitions are loaded before custom definitions. A custom package cannot replace a built-in ID.

## Package identity and metadata

Every package contains:

- A permanent lowercase package ID
- Display name
- Semantic version
- Author or company
- Website
- License
- Category
- Search tags
- Display order
- Description

The package ID becomes the folder name and should not change after publication. Publish improvements using a newer `version` while retaining the same package ID.

## Form-theme authoring

A form-theme package contains:

```text
<theme-id>/
├── theme.json
├── preview.html
├── style.css
├── script.js
├── README.md
└── components/
    ├── field.html.tpl
    ├── textarea.html.tpl
    ├── select.html.tpl
    ├── checkbox.html.tpl
    ├── button.html.tpl
    └── form.html.tpl
```

The studio accepts a representative form in **Preview form HTML**. The preview is only for authoring and marketplace presentation. It is not parsed into graph nodes. The component templates define the HTML generated by real View Form, Text Input, Email Input, Select, Checkbox, Button, and related nodes.

A theme therefore controls presentation but does not define the form's fields or data flow. Add and connect those form/input nodes normally in the View Builder; the selected theme is applied when they compile.

### CSS isolation

Every theme CSS rule must use `{{scope}}` as its root:

```css
{{scope}} .thv-field input {
    border-color: var(--thv-theme-border);
}
```

At compilation time, the IDE replaces `{{scope}}` with the owning View's isolated theme selector. A theme cannot be saved when its CSS does not use this token.

### Component-template tokens

The studio validates these required tokens:

| Template | Required tokens |
|---|---|
| Field, Textarea, Select | `{{wrapper_attributes}}`, `{{label_html}}`, `{{control_html}}`, `{{error_html}}` |
| Checkbox | `{{wrapper_attributes}}`, `{{control_html}}`, `{{label_html}}`, `{{error_html}}` |
| Button | `{{wrapper_attributes}}`, `{{control_html}}` |
| Form | `{{wrapper_attributes}}`, `{{children_html}}` |

The same field template is used for text, email, password, number, date and file inputs.

### Semantic palettes

Themes should define semantic colors instead of component-specific colors. Standard tokens include:

```text
primary, secondary, surface, surface_alt, text, muted, border,
danger, on_primary, success, warning, info
```

Multiple named palettes can be included in one package. The palette manager lets authors create, duplicate, select, rename, delete, and set the default palette. Each semantic token has a text value and color picker, and the selected palette updates the sandbox preview immediately. The exported `theme.json` still stores the same portable palettes object.

### JavaScript

Theme JavaScript is optional. Prefer behavior scoped to the generated theme/View instead of global `document.querySelector(...)` calls. Global queries generate a warning because more than one themed View may be present on a page.

## HTML-snippet authoring

An HTML-snippet package contains:

```text
<snippet-id>/
├── snippet.json
├── snippet.html
├── style.css
├── script.js
└── README.md
```

Snippet HTML must be a reusable fragment. Do not include `<html>`, `<head>`, `<body>`, `<style>` or `<script>` tags. CSS and JavaScript belong in their separate source editors.

When a snippet is chosen in the HTML Component Designer, its HTML, CSS, and JavaScript are copied into one normal **HTML Design Component** node. Raw `<input>`, `<select>`, and `<button>` elements inside the snippet remain markup inside that component; they are not automatically extracted into separate View Builder nodes. Use normal Form/Input nodes when each field must have its own graph configuration or connection.

Snippet CSS is scoped by the HTML Component compiler. Avoid global selectors such as `html`, `body` and `:root` because they cannot behave like normal component selectors.

Snippet JavaScript receives the generated component wrapper as `root`:

```js
const button = root.querySelector('[data-action]');
```

Prefer `root.querySelector(...)` over querying the complete document so multiple instances can run independently.

HTML snippets inherit the owning View's semantic form-theme variables, allowing a snippet and its surrounding form controls to share one palette.

## Preview and validation

The studio preview runs in a sandboxed iframe. Source is not executed by PHP while it is imported or saved.

The validation panel checks package identity and source requirements before save. It also provides warnings for patterns that are technically allowed but reduce portability, including document-wide JavaScript selectors and global CSS selectors.

Server-side validation repeats the important checks. Importing a ZIP cannot bypass the custom-package restrictions or overwrite a built-in package.

## Import and export

**Export ZIP** creates a self-contained package with its manifest, source files and generated README. Only custom packages can be exported from the Asset Studio.

**Import ZIP** accepts a package whose root contains either:

```text
theme.json
```

or:

```text
snippet.json
```

A ZIP may contain one wrapping folder; it is normalized during import. Imported packages are always stored as custom assets. Importing a newer package with the same custom ID updates that custom package.

The maximum package upload size is 20 MB.

## Backup and migration

Custom marketplace packages are included in **Export All IDE Data** and restored by **Import All IDE Data**. Clearing all IDE data also removes custom marketplace assets while leaving bundled assets intact.

## Marketplace publishing recommendations

Before publishing a package:

1. Keep the package ID stable across versions.
2. Use a semantic version such as `1.2.0`.
3. Include a clear description, category, tags, author and license.
4. Test responsive behavior and more than one component instance.
5. Use semantic theme variables and scoped selectors.
6. Avoid dependencies on external JavaScript or CSS files.
7. Export the package from the Asset Studio and re-import it into a clean installation as a final test.

The ZIP format is intentionally self-contained so a future marketplace can deliver the package directly to the IDE without translating its contents.
